# ADR-0002：单仓库与模块化单体

- 状态：Accepted
- 日期：2026-01-12
- 决策者：`@architecture-team`
- 会签：`@platform-team`、`@sre-team`
- 影响范围：`apps/`、`packages/`、`agents/`、`schemas/`、`evals/`、`infra/`、`tests/`
- 相关文档：[`../index.md`](../index.md)、[`../dependency-rules.md`](../dependency-rules.md)、[`0001-record-architecture-decisions.md`](0001-record-architecture-decisions.md)、[`../../../ARCHITECTURE.md`](../../../ARCHITECTURE.md)

## 背景

平台需要同时支撑多个业务 Agent，并且这些 Agent 共享同一套契约、策略引擎、状态存储、观测与评测设施。

当时的实际约束：

| 约束 | 具体表现 |
| --- | --- |
| 共享面大 | 每个 Agent 都依赖 `packages/agent-contracts/`、`packages/policy-engine/`、`packages/state-store/`、`packages/observability/` |
| 变更频繁且横切 | 契约、策略、授权网关的改动会同时影响所有 Agent，且必须原子生效 |
| 团队规模小 | 平台团队与业务团队合计不超过数十人，无法承担多仓库的版本协调成本 |
| 强合规要求 | 需要统一审计、统一数据分类、统一保留策略，跨仓库一致性难以证明 |
| 编码 Agent 参与开发 | 编码 Agent 需要一次加载完整上下文；跨仓库上下文拼接会显著降低改动正确率 |
| 评测依赖共享数据 | `evals/shared-datasets/`、`evals/baselines/` 被所有 Agent 复用 |

同时，每个 Agent 的所有者、发布节奏、风险等级都不同，需要独立的部署与回滚单元。

## 决策

1. 采用单仓库（one repository），所有业务 Agent、应用与平台包放在同一个仓库内。
2. 采用模块化单体（modular monolith）作为代码组织形态：一个仓库，多个模块，模块之间通过公开接口通信。
3. 每个业务 Agent 是 `agents/<agent-name>/` 下的一个独立模块，内部布局统一（`AGENTS.md`、`agent.yaml`、`src/`、`prompts/`、`tools/`、`tests/`）。
4. 模块边界通过六层依赖方向强制：`Types -> Config -> Repo -> Service -> Runtime -> UI`。跨模块访问只允许通过公开入口。
5. 模块边界由自动化检查执行，不依赖约定与自觉：[`../../../scripts/check-architecture.py`](../../../scripts/check-architecture.py) 在 CI 中拒绝违规依赖。
6. 部署单元与代码模块一一对应。模块化单体不等于单体部署：`apps/agent-api`、`apps/worker`、`apps/admin-console` 以及每个 Agent 的运行时单元可独立构建、独立发布、独立回滚。
7. 模块之间的运行时通信优先使用进程内接口调用；只有当模块需要独立部署、独立权限、独立失败域或独立扩缩容时，才允许拆成独立服务，并且必须写 ADR。
8. 路径所有权通过 `CODEOWNERS` 声明，跨模块改动必须得到相关模块所有者批准。
9. 共享契约（`packages/agent-contracts/`、`schemas/`）的破坏性变更需要 ADR，并由 `@architecture-team` 评审。

## 后果

### 正面

- 横切改动可以原子提交：契约、策略、所有消费者在同一个 PR 内保持一致，不存在版本错配窗口。
- 依赖方向可被机器检查，模块化不会随时间退化为「什么都互相 import 的泥球」。
- 编码 Agent 可以在一次上下文加载中获得完整规则、契约与相邻模块实现，改动正确率显著提高。
- 共享设施只有一份实现：授权网关、状态存储、遥测、评测套件不需要为每个 Agent 重复建设。
- 统一审计与数据分类：合规证据来自一个仓库、一套流水线。
- 评测基线可以跨 Agent 复用，回归与安全套件集中维护。

### 负面

- 仓库体积与克隆时间随时间增长。缓解方式是按模块增量执行 CI，只跑受影响的模块及其消费者。
- 单仓库容易产生隐式耦合。缓解方式是依赖检查脚本加包边界规则，违反即失败。
- 一次错误的共享改动可能同时影响所有 Agent。缓解方式是契约测试、分阶段发布、以及每个 Agent 的独立回滚能力。
- 构建缓存与任务编排成为必需品。缓解方式是 `tooling/task-runner/` 承担受影响模块分析与任务缓存。
- 权限粒度只能到路径，不能到仓库。缓解方式是 `CODEOWNERS` 加分支保护，生产凭据不进入仓库，运行时按最小权限授予。

### 中性

- 版本号从「仓库版本」变成「模块版本」。发布流水线需要按模块生成版本与变更说明。
- 团队协作从「跨仓库 PR」变成「跨路径 PR」，评审负载从合并冲突转移到代码评审。

## 替代方案

| 方案 | 否决原因 |
| --- | --- |
| 每个 Agent 一个仓库（polyrepo） | 共享契约的横切变更需要协调 N 个仓库的发布顺序，版本错配窗口无法消除；评测基线、策略引擎、授权网关需要多份实现或跨仓库版本管理；编码 Agent 无法在一次加载中取得完整上下文；团队规模不足以承担版本协调成本 |
| 单应用加目录划分（无模块边界） | 没有可检查的边界，任何目录都可能被任意 import，长期必然退化为泥球；无法做模块级所有权与受影响范围分析；无法独立回滚单个 Agent |
| 每个 Agent 一个独立微服务加独立仓库 | 每个服务都需要独立的契约发布、CI、部署、凭据与审计链路，运维成本远超收益；进程内调用被替换为网络调用，延迟与失败模式复杂度上升；当前规模下没有独立扩缩容需求 |
| 单仓库但共享库以私有包注册表发布，仓库内按包引入 | 引入了注册表作为额外基础设施与发布瓶颈；跨包改动需要在注册表发布后才可见，破坏了原子提交；对编码 Agent 而言多了一层不可见状态 |
| 单仓库加动态依赖注入容器，运行时决定层关系 | 运行时决定的依赖关系无法被静态检查，依赖方向规则失效；故障定位难度上升；与本仓库「规则必须有机器检查」的原则冲突 |

## 验证方式

- 依赖方向：[`../../../scripts/check-architecture.py`](../../../scripts/check-architecture.py) 在 CI 中执行，违规即失败。
- 契约兼容性：`tests/contracts/` 的契约测试覆盖公开接口。
- 模块独立性：每个 Agent 的清单由 [`../../../scripts/check-agent-manifests.py`](../../../scripts/check-agent-manifests.py) 校验，包含所有者、模型、工具与限额。
- 发布独立性：`.github/workflows/release.yml` 按模块生成发布单元；单个 Agent 的回滚不影响其他 Agent。
- 所有权：`CODEOWNERS` 中的路径规则与模块目录一一对应。

## 退出条件

出现下列任一情况时，重新审视本决策：

1. 单个模块需要独立于仓库的发布节奏与权限模型，且无法通过现有分支保护与流水线满足。
2. 仓库克隆、构建或 CI 时长增长到阻碍日常开发，且受影响模块增量执行已经无法缓解。
3. 团队规模与组织结构变化，使多仓库的版本协调成本低于单仓库的协调成本。
4. 合规要求强制要求代码与部署单元在物理上分离。

拆出模块必须遵循 [`../../../ARCHITECTURE.md`](../../../ARCHITECTURE.md) 第 9 节：只有需要独立部署、独立权限、独立失败域或独立扩缩容时才拆分，并写新 ADR 取代本决策的相关条款。
