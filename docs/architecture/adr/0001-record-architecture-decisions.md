# ADR-0001：记录架构决策

- 状态：Accepted
- 日期：2026-01-05
- 决策者：`@architecture-team`
- 影响范围：全仓库
- 相关文档：[`../index.md`](../index.md)、[`../dependency-rules.md`](../dependency-rules.md)、[`../../../ARCHITECTURE.md`](../../../ARCHITECTURE.md)

## 背景

本仓库同时承载编码 Agent 工程体系与运行时 Agent 应用体系。两个体系里，架构决策会被反复重新讨论：

- 新加入的工程师或编码 Agent 看不到过去的取舍，倾向于按局部最优重做一遍。
- 决策只存在于 PR 评论、聊天记录或某个人的记忆里，无法被检索，也无法被引用。
- 同一个问题在不同模块得到不同答案，例如有的 Agent 用直接 HTTP 调模型，有的用 `ModelProvider`。
- 编码 Agent 缺少可加载的决策上下文，容易生成与既有架构冲突的实现。

已有的 `ARCHITECTURE.md` 描述「现在的架构是什么」，但不记录「为什么是这样」以及「哪些方案被否决过」。缺少后者时，被否决的方案会周期性地重新出现。

## 决策

1. 本仓库使用架构决策记录（ADR）保存重要架构决策。
2. ADR 存放在 `docs/architecture/adr/`，命名规则为 `NNNN-<kebab-case-title>.md`，四位数字连续编号，永不重复使用。
3. ADR 一经接受即为不可变历史记录。内容需要改变时，写一条新 ADR，并把旧 ADR 的状态改为 `Superseded by ADR-NNNN`。
4. ADR 使用统一格式：标题、元信息、背景、决策、后果、替代方案。需要时可增加「验证方式」与「退出条件」小节。
5. 以下情况必须写 ADR：
   - 共享契约的破坏性变更（`packages/agent-contracts/`、`schemas/`）
   - 新增、删除或改变 Provider 接口
   - 新增顶层目录，或改变层级划分
   - 引入新的外部依赖类别（新数据库、新消息队列、新模型供应商类别）
   - 把模块提升为独立服务，或把独立服务合并回仓库
   - 长期偏离依赖规则的豁免
6. 以下情况不写 ADR：局部实现细节、命名、格式、测试组织、不影响其他模块的重构。这些写在 PR 描述或执行计划里。
7. 状态取值只有五个：`Proposed`、`Accepted`、`Rejected`、`Deprecated`、`Superseded by ADR-NNNN`。
8. 生命周期：作者提交 `Proposed` 状态 ADR 的 PR，评审通过后在同一 PR 内改为 `Accepted`，并同步更新代码与受影响的文档。被否决的方案保留 `Rejected` 状态，不删除。
9. 每个 ADR 由 `@architecture-team` 评审。涉及安全边界、授权、密钥或数据分类的 ADR 必须由 `@security-team` 会签。

## 后果

正面：

- 决策可检索、可引用、可追溯，减少重复讨论。
- 编码 Agent 能加载 ADR 目录作为上下文，减少与既有架构冲突的实现。
- 被否决的方案连同否决理由一起保存，避免周期性地重新提出。
- 变更评审有明确依据：判断一个改动是否需要架构评审，看它是否命中第 5 节清单。

负面：

- 每个重要决策增加一次写作与评审成本。为了控制成本，第 6 节明确排除了不影响其他模块的改动。
- ADR 不可变，意味着旧 ADR 里会存在过时描述。缓解方式是强制在新 ADR 中引用被取代的编号，并同时更新 `docs/architecture/` 下的规则文档。
- 状态维护依赖纪律。缓解方式是 [`../../../scripts/check-doc-links.py`](../../../scripts/check-doc-links.py) 校验 ADR 索引链接，评审清单要求检查状态字段。

中性：

- ADR 是文档资产，不参与运行时。它不改变任何代码路径，只改变决策过程的可追溯性。

## 替代方案

| 方案 | 否决原因 |
| --- | --- |
| 不记录决策，靠 PR 历史与聊天记录 | 不可检索，跨模块不可见，编码 Agent 无法加载 |
| 把决策写进 `ARCHITECTURE.md` 正文 | 该文档描述当前状态，会被反复改写，历史取舍丢失 |
| 使用外部 Wiki 或工单系统 | 与代码分离，无法在同一个 PR 内评审，链接易失效 |
| 使用 RFC 流程，不做编号归档 | 缺少稳定编号，无法被其他文档精确引用 |
| 使用注释形式的轻量决策记录 | 与代码耦合，模块重构时丢失，且无法记录被否决的方案 |

## 验证方式

- 目录存在性：`docs/architecture/adr/` 下的文件必须符合 `NNNN-<title>.md` 命名。
- 索引一致性：`docs/architecture/index.md` 的 ADR 表必须列出每个 ADR 及其状态。
- 链接可达：[`../../../scripts/check-doc-links.py`](../../../scripts/check-doc-links.py) 校验 ADR 之间的相对链接。
- 评审清单：架构评审技能 `review-architecture` 检查元信息字段是否完整、状态是否与实际一致。

## 退出条件

当 ADR 数量超过团队维护能力，或出现更适合的决策记录工具且能同时满足「与代码同 PR 评审」「可被编码 Agent 加载」「稳定编号可引用」三项要求时，重新审视本决策。
