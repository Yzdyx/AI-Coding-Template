# 核心设计信念

本文件列出平台的六条核心设计信念。信念是设计决策的默认答案：当没有更强理由时，按信念行事。每条信念都给出理由与可检验的判定标准，避免它退化成口号。

## 0. 信念一览

| 编号 | 信念 | 一句话 |
| --- | --- | --- |
| B1 | 渐进式上下文加载 | 只加载当前任务需要的知识 |
| B2 | 文档即代码 | 文档与代码同 PR、同评审、同版本 |
| B3 | 边界优于提示词 | 用结构约束行为，而不是靠措辞 |
| B4 | 自动化优于说明 | 重要规则必须有机器检查 |
| B5 | 小步变更 | 每次改动尽可能小且可独立验证 |
| B6 | 不可逆操作需人工审批 | 高风险与不可逆动作停下等人 |

## B1 渐进式上下文加载（progressive context loading）

**理由**：模型与人的注意力都是有限资源。把整个仓库塞进上下文会稀释关键信息，推高成本，并提高出错概率。知识应当分层索引、按需读取，而不是一次性全量加载。

**判定标准**：

- 仓库根 [`../../AGENTS.md`](../../AGENTS.md) 只做导航与稳定约束，保持简短。
- 详细知识放在被索引的文档里，由入口文档给出路径，读者按需打开。
- 每个业务 Agent 的本地 `AGENTS.md` 只描述本模块，不复制平台级规则。

**反例**：把全部编码规范、依赖规则与运维手册直接写进根 `AGENTS.md`，导致每次任务都要加载全部内容。

## B2 文档即代码（documentation as code）

**理由**：与代码分离的文档必然腐化。文档只有与代码同 PR、同评审、同版本，才可能长期保持真实。评审流程是文档质量的唯一可持续保障。

**判定标准**：

- 规则文档与它描述的代码在同一个 PR 内更新。
- 文档变更走 PR 评审，遵循 [`../../CODEOWNERS`](../../CODEOWNERS) 的路径所有权。
- 文档语言、命名与目录规则在仓库内统一，见 [`../../README.md`](../../README.md)。

**反例**：把接口说明放在外部 Wiki，与实现长期脱节，编码 Agent 无法加载。

## B3 边界优于提示词（boundaries over prompts）

**理由**：提示词是概率性的，边界是确定性的。用模块边界、类型、Schema、权限策略约束行为，比反复打磨提示词更可靠、更可测试、更可审计。

**判定标准**：

- 能用一个类型、一个 JSON Schema 或一条依赖规则表达的约束，不写成提示词里的祈使句。
- 权限与授权由 [`../architecture/dependency-rules.md`](../architecture/dependency-rules.md) 描述的 Provider 与策略引擎执行，不靠模型自觉。
- 提示词只承载语气、风格与任务意图，不承载安全边界。

**反例**：靠系统提示要求模型「不要调用删除接口」，而不是在策略引擎里直接拒绝该调用。

## B4 自动化优于说明（automation over instructions）

**理由**：说明会被忽略，检查不会被忽略。一条重要规则如果没有机器检查，它在实践中只是建议。强制力必须来自流水线，而不是来自文档的语气。

**判定标准**：

- 每条强制规则都指向一个检查脚本或测试，例如 [`../../scripts/check-architecture.py`](../../scripts/check-architecture.py) 与 [`../../scripts/check-doc-links.py`](../../scripts/check-doc-links.py)。
- 新增强制规则时，同时提交对应的检查改动，见 [`../../ARCHITECTURE.md`](../../ARCHITECTURE.md) 第 4 节。
- 违规在合并前被拒绝，而不是在事后被发现。

**反例**：文档写明「禁止跨包深层导入」，但没有检查脚本，违规代码照样合入。

## B5 小步变更（small changes）

**理由**：小改动容易评审、容易回滚、失败影响面小。大改动难以定位问题，也难以安全发布。可独立验证的改动是可靠交付的最小单位。

**判定标准**：

- 一个任务一个 PR，改动限制在任务元数据声明的 `scope.paths` 内。
- 超出声明范围的改动拆成新任务，不搭车提交。
- 跨模块改动先写执行计划，见 [`../PLANS.md`](../PLANS.md)。

**反例**：借修一个 bug 之名，顺带做全仓库重命名与重构，使评审无法聚焦。

## B6 不可逆操作需人工审批（human approval for irreversible actions）

**理由**：有些动作无法撤销：支付、发送、删除、生产写入。一旦错误执行，代价不可逆。对这类动作，机器必须停下等人确认，并留下审批记录。

**判定标准**：

- 高风险与不可逆动作前必须有人工审批节点，且记录审批人身份。
- 审批不是提示词里的请求，而是工作流中一个阻塞节点。
- 生产写入与破坏性操作默认关闭，需要显式开启并留痕。

**反例**：Agent 直接执行生产环境删除，事后再通知人类。

## 信念与强制检查的对应

信念不是并列的口号，每条都能落到一个可执行的检查或流程上。

| 信念 | 主要落地方式 | 检查或证据 |
| --- | --- | --- |
| B1 渐进式上下文加载 | 分层索引文档 + 每模块 `AGENTS.md` | [`../../scripts/check-doc-links.py`](../../scripts/check-doc-links.py) 保证索引可达 |
| B2 文档即代码 | 同 PR 更新 + 路径所有权 | [`../../CODEOWNERS`](../../CODEOWNERS)、PR 评审 |
| B3 边界优于提示词 | 类型、Schema、策略引擎 | [`../../scripts/check-architecture.py`](../../scripts/check-architecture.py)、[`../architecture/dependency-rules.md`](../architecture/dependency-rules.md) |
| B4 自动化优于说明 | 仓库级检查脚本 + CI | [`../../ARCHITECTURE.md`](../../ARCHITECTURE.md) 第 4 节 |
| B5 小步变更 | 任务元数据声明 scope | [`../PLANS.md`](../PLANS.md) 的元数据格式 |
| B6 不可逆操作需人工审批 | 工作流审批节点 | [`../SECURITY.md`](../SECURITY.md) 的审批关卡 |

## 如何使用本文件

1. 做设计决策时，先按信念给出默认答案，再判断是否有更强理由偏离。
2. 偏离信念时，必须在 [`../PLANS.md`](../PLANS.md) 描述的决策日志里记录原因、影响范围与退出条件。
3. 发现某条信念在实践中持续被违反，说明要么信念过时，要么缺少检查。先补检查，再考虑修改信念。
4. 修改本文件属于设计评审范围，由 `@architecture-team` 评审，并同步更新 [`index.md`](index.md) 中的状态。
